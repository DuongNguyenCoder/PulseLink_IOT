# PulseLink API — Backend Instructions

These rules supplement the repository-wide `AGENTS.md`. If a rule conflicts, stop and report the conflict; do not silently choose a different architecture.

## Scope and architecture

- Keep the API as a modular monolith using Node.js ESM, TypeScript, Fastify 5, Zod, Prisma 7 and PostgreSQL.
- Keep HTTP mapping in routes, business rules in services, and persistence through Prisma. Add repositories only when they provide a useful boundary.
- Business routes are versioned under `/v1`; health and operational routes remain under `/health`.
- Do not add microservices, brokers, Redis, CQRS or another framework without an approved decision.

## Input, errors and logging

- Validate every external body, param and query with Zod at runtime.
- Use Fastify's built-in Pino logger. Never use `console.log`.
- Redact authorization headers, device credentials, FCM tokens, database URLs and complete event payloads.
- Map validation, authentication, authorization, conflict, rate-limit, dependency and unexpected failures to the documented API error contract.
- Never return stack traces, SQL, internal paths or secret material.

## Device and event invariants

- A device identifier is not a credential. Device authentication must verify a secret-derived proof and the device status.
- Derive `storeId` from the authenticated device; never trust a store identifier supplied by the device.
- Store only a SHA-256 verifier for the approved high-entropy bearer token. Never store plaintext credentials or reversible ciphertext. A newly issued token is shown once and is never logged.
- `eventId` is generated by firmware once and may be reused for retries during the current active session. No persistent retry survives reboot or power loss. Durable database uniqueness is the idempotency source of truth.
- A successful event response is sent only after the event is durably stored. Duplicate handling must be explicit and tested.
- Keep event timestamps in UTC and bound diagnostic payloads before persistence.

## Database safety

- Use the configured Prisma 7 PostgreSQL adapter and one PrismaClient per API process.
- Treat migrations as append-only. Never edit or delete an existing migration.
- Never run `migrate reset`, `db push`, destructive SQL or production migration without explicit user approval.
- Do not inspect or print `.env` values, database URLs or credentials.

## Verification and handoff

- Before changes, inspect the relevant docs, schema, migrations, package versions and current diff.
- Add tests for success, invalid input, authentication/authorization, idempotency and relevant failure/retry paths.
- Run typecheck, build, relevant tests and Prisma validation when applicable; report only observed results.
- Keep generated client output and the active Prisma CLI configuration unambiguous. Do not delete duplicate-looking files until runtime and CLI usage are verified.
