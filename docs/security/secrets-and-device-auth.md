# Secrets and Device Authentication

## Secrets

- Keep local values in `.env`; commit `.env.example` only.
- Rotate any secret that was pasted into a public issue, source file, commit, or shared log.
- Never log `Authorization`, device secrets, FCM registration tokens, database URLs or full push payloads.
- Store only a SHA-256 verifier for the high-entropy device bearer token, never the plaintext token. Verify by hashing the received token and comparing the fixed-length digest with constant-time comparison. This is suitable because the token is generated by a CSPRNG and is not a human password; do not use this rule for low-entropy passwords.

## Device authentication

- A `deviceKey` is an identifier, not a secret.
- Device requests use `Authorization: Bearer <deviceToken>` over HTTPS.
- Require authentication for event ingestion.
- Plan a per-device credential rotation/revocation path.
- Use HTTPS outside local development.
- Apply payload size limits and rate limiting before production.
- Do not allow a device to choose arbitrary `storeId`; derive its store from the authenticated device record.

## Identity and onboarding boundaries

- A signed-in Owner account identity and its Store-scoped authorization are separate from device authentication.
- The initial Owner is created through controlled provisioning over the protected API; public signup must not create administrative Store/device authority.
- An operator is an authenticated Owner principal with Store-scoped permission; a shared administrator account is not the default trust model.
- A user may belong to multiple Stores, but each sensitive operation must resolve one authorized active Store membership and fail closed when it is missing or ambiguous.
- A device `deviceId` or `deviceKey` identifies hardware but is never a credential.
- A bootstrap secret used for physical-button-gated SoftAP pairing is single-use and time-limited by the future onboarding contract. It is not the operational device bearer token.
- An app installation and FCM registration token identify a push destination only. An FCM token is not a user identity or proof of Store authorization.
- Resetting hardware does not release backend ownership. Store transfer and credential revocation require an authorized backend operation.
- Physical reset removes local Wi-Fi/configuration and, when required, the local operational token; the backend keeps Device ID, ownership, events and audit records. The UI should represent the resulting reconnection state explicitly.
- Audit records for sensitive state changes and the state change itself must commit in one database transaction; audit retention is 365 days. This is a design invariant, not a claim that the current runtime implements audit persistence.
- FCM delivery is best-effort and transactional outbox is outside the MVP.

## Audit data handling

AuditEvent metadata is generated from an explicit allowlist. Passwords, access or
refresh tokens, reset/verification/bootstrap/device/FCM tokens, FCM ciphertext,
authorization headers, cookies and key material are prohibited. Audit writes are
transactional with the protected business mutation; an audit failure must roll
back that mutation. Application append-only behavior does not replace database
privilege controls. The retention policy is 365 days, with operational cleanup
deferred until a reviewed retention procedure exists.

## Logs

- Log request ID, route, status, duration and non-sensitive device ID when appropriate.
- Redact authorization headers and tokens.
- Avoid logging complete event payloads unless each field has been reviewed as non-sensitive.
- Do not log bearer tokens or Authorization headers. A bearer token does not bind a request to its method, path or body; rely on TLS, rate limits and durable event idempotency until a separately approved request-signing protocol exists.
