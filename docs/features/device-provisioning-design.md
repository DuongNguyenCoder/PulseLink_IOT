# PulseLink Device Provisioning Protocol — Design Proposal

Status: `PARTIAL` — J.2 schema foundation is implemented; J.3 provisioning
service/routes and J.4 firmware/commissioning tool are not implemented. Owner
approval is still required for the decisions marked `OPEN`.

## 1. Current repository baseline

The repository currently contains:

- `Device` with `id`, public `deviceKey`, `deviceSecretHash`, `status`, `storeId`
  and device metadata. The existing `DeviceStatus` values are `PENDING`,
  `ONLINE`, `OFFLINE` and `DISABLED`.
- `StoreMembership` and Owner authorization runtime for Store-scoped requests.
- Account/session/AppInstallation authentication with DB-authoritative Account
  status and `authVersion` checks.
- `AuditEvent` persistence and a shared allowlisted metadata writer that can run
  inside a Prisma transaction.
- No device provisioning routes, device bearer middleware, provisioning service,
  mobile source, or ESP32 source implementation. The `firmware/esp32`,
  `apps/mobile` and `packages/contracts` trees currently contain no source that
  establishes a wire contract.
- Legacy `StaffPushToken` remains separate. It is not mapped to AppInstallation
  and is not part of provisioning.

The J.2 schema now represents enrollment/provisioning state separately from the
existing operational status, stores enrollment public-key metadata, and adds a
durable provisioning-session state. `Device.storeId` remains required by the
existing ownership model; an unregistered physical unit must therefore be
registered by the USB commissioning tool before a Store-scoped provisioning
session can be created.

## 2. Proposed trust model

There are three separate identities/secrets:

1. `deviceKey`: public, stable device identifier. It is not an authenticator.
2. Bootstrap credential: short-lived, one-time enrollment credential. The API
   stores only a verifier and attempt metadata.
3. Operational device token: high-entropy bearer credential generated by the
   backend. The database stores only its SHA-256 verifier in
   `Device.deviceSecretHash`; the device stores the plaintext only in protected
   NVS and receives it only at successful redemption.

The operational protocol remains HTTPS plus `Authorization: Bearer <deviceToken>`.
This proposal does not replace it with HMAC or AES-GCM.

Wi-Fi association, SSID knowledge, IP visibility, Device ID knowledge and a
successful SoftAP connection are not ownership evidence.

## 3. Provisioning sequence

```mermaid
sequenceDiagram
    participant O as Owner app
    participant C as USB commissioning tool
    participant A as PulseLink API
    participant D as ESP32 device
    participant P as PostgreSQL

    C->>A: Register device identity over controlled USB commissioning flow
    A->>P: Store device identity/enrollment metadata
    D->>D: Registered identity exists; no operational token
    D->>D: Owner presses physical button; open short provisioning window
    D-->>O: SoftAP discovery + device public identity/challenge
    O->>A: Create provisioning session for deviceKey and Store
    A->>P: Verify Account, email, active OWNER membership, Device state
    A->>P: Create session; store bootstrap verifier, expiry and attempt state
    A-->>O: sessionId, challenge, one-time bootstrap secret/transport data
    O->>D: Configure Wi-Fi and pass bootstrap material over protected local flow
    D->>A: Redeem bootstrap over HTTPS with deviceKey, challenge, physical proof
    A->>P: Lock session; verify verifier, TTL, attempts and physical proof
    A->>P: Atomically mark bootstrap used, store device token hash, update state,
    A->>P: append AuditEvent
    A-->>D: Plaintext operational token exactly at redemption
    D->>D: Store token in protected NVS; erase bootstrap/Wi-Fi transient data
    D->>A: Optional completion acknowledgement using operational token
    A-->>O: Provisioning state becomes complete/online when confirmed
```

### 3.1 Device identity

Recommended direction: retain the backend `Device.id` as the internal resource
identifier and use `deviceKey` as the stable public/factory identifier. The
identifier must be generated from a controlled factory/enrollment process or a
cryptographically random backend process; it must not be inferred from SSID,
MAC address or IP address.

For the approved prototype, the USB commissioning tool is the controlled
enrollment source of truth. It must not create a Device record from an
arbitrary client-supplied identifier without the controlled commissioning
authorization. Production manufacturing key injection and stronger device
identity remain separate hardening decisions.

### 3.2 Physical button and LED

Proposed firmware behavior:

- A long physical-button press opens a short local provisioning window.
- The device generates a fresh, single-use physical challenge/proof nonce and
  displays provisioning mode using a documented LED pattern.
- A timeout returns the device to normal idle/error indication.
- A reset press clears local Wi-Fi and operational credential material but does
  not signal backend ownership transfer or delete backend history.

A random nonce alone is not a strong proof if an attacker can impersonate the
device. The preferred proof is a device-bound factory key/attestation or an
equivalent hardware-backed identity. The repository does not currently verify
that such a key exists in the ESP32 provisioning design. This is an `OPEN`
security decision and a blocker for claiming strong physical proof.

### 3.3 SoftAP and Wi-Fi

The SoftAP is a transport bootstrap channel only:

- The app discovers the device and exchanges Wi-Fi configuration only while the
  physical provisioning window is open.
- SoftAP connectivity does not authorize a Store claim.
- The local channel must use an authenticated/pinned device identity or an
  equivalent protected commissioning mechanism before J.2 implementation.
- Wi-Fi credentials are written to NVS only after validation and are cleared on
  physical reset according to firmware policy.

The exact SoftAP password, local TLS/pinning UX and whether a QR/label is used
are `OPEN`. A plaintext unauthenticated local HTTP exchange is not an acceptable
final protocol.

## 4. Bootstrap lifecycle

Baseline constraints:

- TTL: 30 minutes.
- Maximum failed attempts: 5.
- Store only a verifier/hash; never persist or log the plaintext bootstrap
  secret.
- Redemption is one-time, atomic and concurrency-safe.
- Operational credential is a separate secret and cannot redeem bootstrap.

Proposed state transitions:

```text
CREATED -> ACTIVE -> REDEEMED
                    └-> EXPIRED
                    └-> LOCKED (five failed attempts)
ACTIVE  -> CANCELLED (Owner/API cancellation)
```

Each failed redemption increments the attempt counter using a conditional
transaction. Attempts at or above five, expired sessions and already redeemed
sessions fail with the same non-sensitive error. Reset/cooldown policy,
reissue policy and whether a failed session is permanently locked or may be
replaced are `OPEN`.

The redemption transaction must lock the provisioning session and the Device
row, verify all conditions, consume the bootstrap verifier, rotate/revoke any
previous operational credential as approved, and append the audit event before
commit.

## 5. Device state machine

```text
UNREGISTERED
    | controlled enrollment / inventory
    v
PENDING_PROVISIONING
    | Owner session + physical proof + bootstrap redemption
    v
PROVISIONED
    | heartbeat/event authentication
    v
ONLINE <--> OFFLINE
    |
    +--> NEEDS_RECONNECTION (credential lost/reset or recovery required)
    |
    +--> DISABLED (authorized backend action)

PENDING_PROVISIONING --timeout/failure--> PENDING_PROVISIONING + audit
PROVISIONED/NEEDS_RECONNECTION --authorized reprovision--> PROVISIONED
```

The current Prisma enum cannot represent `UNREGISTERED`,
`NEEDS_RECONNECTION` or a durable provisioning-session failure state. J.2 must
choose between an additive provisioning-state enum/fields or a separate
provisioning-session model. No transfer or multiple active Owner behavior is
assumed here.

Only the current authorized Store Owner may start or complete provisioning for
an already-owned Device. Physical reset is not transfer. A transfer workflow
requires a separate Owner-approved policy and is out of scope.

## 6. Proposed API contract

These are proposals, not implemented endpoints.

### 6.1 Owner application endpoints

#### `POST /v1/stores/:storeId/devices/provisioning-sessions`

Actor: authenticated, email-verified Account with active `OWNER` membership.

Request:

```json
{
  "deviceKey": "public-device-key",
  "idempotencyKey": "client-generated-request-id"
}
```

Response contains only non-secret session data plus the bootstrap material
needed by the approved commissioning UX. A bootstrap secret is returned at most
once and is never logged or placed in AuditEvent metadata.

The server verifies Store membership and Device scope. The transaction creates
or updates only a pending provisioning session and writes
`DEVICE_PROVISIONING_STARTED`. A repeated idempotency key returns the same
non-secret session result; a conflicting key/resource pair returns `409`.

Suggested errors: `401`, `403`, `404`, `409`, `429`, `503`.

#### `POST /v1/stores/:storeId/devices/:deviceId/provisioning-cancel`

Actor: current active Owner. Cancels an active session, writes
`DEVICE_PROVISIONING_CANCELLED` in the same transaction and does not delete
Device history or release ownership.

#### `POST /v1/stores/:storeId/devices/:deviceId/reconnect`

Actor: current active Owner. Starts a new authenticated recovery/provisioning
session after a physical reset. It must not be callable by another Store Owner
or convert reset into transfer.

The exact path naming and whether cancellation/reconnect are separate endpoints
remain `OPEN`.

### 6.2 Device endpoint

#### `POST /v1/device-provisioning/redeem`

Actor: device presenting the bootstrap credential over HTTPS, not an app-user
JWT.

Request fields:

```json
{
  "deviceKey": "public-device-key",
  "sessionId": "provisioning-session-id",
  "challenge": "session-bound-challenge",
  "physicalProof": "device-bound-proof",
  "idempotencyKey": "device-generated-redemption-id"
}
```

The bootstrap credential is carried in its dedicated Authorization scheme or
header and is never accepted as the operational device bearer token.

On success, the response contains the plaintext operational device token only
for the device redemption response. The API does not provide a later token-read
endpoint. The transaction marks the bootstrap used, stores only the SHA-256
device-token verifier, updates provisioning state and appends
`DEVICE_CREDENTIAL_ISSUED`.

If the response is lost after commit, the safe recovery is an authorized new
reconnection session and credential rotation. The server must not log or later
reveal the old plaintext token.

Suggested errors: `400`, `401`, `409`, `429`, `503`, with generic messages for
invalid/expired/locked bootstrap material.

### 6.3 Operational device authentication

After redemption, normal device endpoints use:

```text
Authorization: Bearer <operational-device-token>
```

The API derives Store ownership from the authenticated Device row. It never
accepts a client-supplied Store ID as authority. Rotation/revocation takes
effect at the next authenticated request; adding an AppInstallation does not
rotate the device token.

## 7. Transaction and audit requirements

All proposed sensitive operations use one transaction:

| Operation | Business state | Audit action |
|---|---|---|
| Start session | provisioning session created/updated | `DEVICE_PROVISIONING_STARTED` |
| Cancel session | session cancelled | `DEVICE_PROVISIONING_CANCELLED` |
| Redeem | bootstrap consumed, credential verifier stored, state changed | `DEVICE_CREDENTIAL_ISSUED` |
| Reconnect/rotate | old verifier revoked, new verifier stored | `DEVICE_CREDENTIAL_ROTATED` |
| Disable/revoke | Device disabled or credential revoked | `DEVICE_CREDENTIAL_REVOKED` |

Audit metadata may contain stable IDs, state names, reason and request ID only.
It must not contain bootstrap secrets, device tokens, hashes/verifiers,
physical proofs, Wi-Fi credentials or raw request bodies. Audit insertion
failure aborts the business transaction. There is no second audit system.

Application append-only behavior still requires database privilege separation;
the recommended production role can INSERT/SELECT AuditEvent but cannot
UPDATE/DELETE it. Retention remains 365 days and no automatic deletion job is
proposed in J.1.

## 8. Threat and failure model

| Scenario | Required behavior | Recovery |
|---|---|---|
| Stranger joins SoftAP | Do not authorize claim; require device-bound proof and API Owner authorization | Close window; restart physical flow |
| Attacker knows Device ID | ID alone is non-secret and insufficient | Require bootstrap + physical proof |
| Bootstrap expired/used | Generic failure; no state change or token issue | Owner starts a new session |
| Five wrong attempts | Atomically lock session; rate-limit and audit security-relevant failure without secrets | New session after policy cooldown/reissue |
| Concurrent redemption | Row lock/conditional update; one succeeds, other gets stable conflict/invalid response | Use winning result or start recovery |
| Owner lacks Store membership | `403`/non-disclosing `404`; no session or ownership change | Obtain valid membership |
| Device belongs to another Store | Reject; never silently move Store | Approved future transfer workflow |
| Response loses issued token | Do not reveal token again; old credential remains recoverable only by authorized rotation | New physical reconnection session |
| Device reboots mid-flow | Treat as incomplete; bootstrap remains subject to its state/expiry | Restart or recover with new session |
| Invalid NVS credential | Device enters recovery indication; API does not accept guessed credentials | Physical reset + Owner reconnection |
| Physical reset after claim | Clear local config only; backend ownership/history remain | Current Owner reprovisions and rotates credential |
| API/PostgreSQL unavailable | Fail closed; do not mark provisioning complete locally | Retry within session policy or start new session |
| Audit insert fails | Roll back provisioning/session/credential change | Retry as a new request after dependency recovery |

## 9. Decisions and blockers

### Existing approved baseline used by this proposal

- Bootstrap TTL 30 minutes and five failed attempts.
- Bootstrap and operational credentials are separate.
- Operational token is backend-generated, one-time displayed and stored only as
  a verifier in PostgreSQL.
- HTTPS bearer authentication remains the device protocol.
- Physical reset does not release backend ownership or delete history.
- Owner authorization is Store-membership based.
- Audit is same-transaction and secrets are excluded.

### Open decisions required before J.2

1. Device/factory enrollment source and whether `deviceKey` is factory-issued or
   backend-issued.
2. Hardware-backed physical proof, factory key/attestation, or an explicitly
   accepted weaker commissioning mechanism.
3. SoftAP security: WPA2 credential, local TLS/pinning, QR/label UX and Wi-Fi
   credential handling.
4. Provisioning-session schema and Device state representation.
5. Bootstrap attempt reset/cooldown/reissue behavior.
6. Exact Owner endpoint names, idempotency semantics and rate-limit thresholds.
7. Whether an explicit redemption acknowledgement is required.
8. Recovery policy when the credential response is lost after server commit.
9. Controlled Owner provisioning actor and permission boundary.
10. Whether transfer ownership is a later phase and its revocation ordering.

## 10. Planned J.2–J.4 changes

- J.2: additive provisioning-session/state schema, bootstrap verifier/attempt
  persistence, device enrollment contract and API service tests.
- J.3: Owner and device provisioning routes, authentication boundaries,
  transactions, AuditEvent integration, concurrency/rate-limit tests.
- J.4: ESP-IDF SoftAP, button/LED state machine, NVS clearing/storage, HTTPS
  redemption and hardware validation. No persistent offline event queue.

No J.2–J.4 implementation is included in this J.1 document-only phase.

## 11. J.1.1 security decision closure

### 11.1 Hardware findings and MVP recommendation

The target is ESP32-S3-WROOM-1 N16R8. The repository contains no ESP-IDF
project, `sdkconfig`, eFuse record, manufacturing manifest or secure-boot/flash-
encryption configuration, so the security features below are capabilities of
the ESP32-S3 platform, not verified properties of a shipped PulseLink device.

Espressif documents ESP32-S3 support for Secure Boot v2, flash encryption and
device-signing facilities such as the Digital Signature/HMAC-backed peripheral.
Flash encryption can protect off-chip flash and secure boot can restrict which
firmware executes, but both require explicit production eFuse/configuration and
manufacturing controls. A firmware readout or flash dump remains a serious
credential-exposure risk if those controls are not enabled and verified.

Recommended MVP commissioning choice: **factory-provision a per-device
bootstrap signing key pair and register its public key before deployment**.

- The private key is generated per device, never shared across devices, and is
  written by a controlled manufacturing station into protected device storage.
- The API stores the public key (or a public-key fingerprint) associated with
  the enrolled `deviceKey`; it does not store the private key or a recoverable
  bootstrap secret.
- The device signs a server/session challenge only while the physical-button
  commissioning window is open. This is bootstrap authentication, not a change
  to the approved operational bearer-token protocol.
- Production release must enable and verify Secure Boot v2, flash encryption,
  restricted debug/download paths and the required eFuse policy before treating
  the private key as protected at rest.
- Key rotation/revocation is represented server-side by enrollment key
  version/status and an authorized reprovisioning transaction. A compromised
  private key is revoked by disabling the enrollment key/device and completing
  an authorized physical recovery; it cannot be recovered from the API.

This is a `PROPOSED` MVP architecture, not an `APPROVED` hardware fact. It is
feasible without treating Device ID, MAC, Wi-Fi or button state as a secret.
The principal limitation is that an attacker who can read flash before the
production security configuration is enabled may copy the bootstrap key and
impersonate the device. Hardware-backed attestation is `OPEN` and is not claimed
to exist in the current product configuration.

Alternatives considered:

| Option | Security/attack resistance | MVP cost and limitation |
|---|---|---|
| Per-device key pair + production Secure Boot/flash encryption | Resists device-ID spoofing and, when configured correctly, local flash readout; supports challenge signatures | Recommended; needs manufacturing station, eFuse policy and hardware validation |
| Per-device secret in ordinary flash/NVS | Stops remote guessing when high entropy, but a flash dump can expose it | Lower cost; acceptable only as a temporary lab mode, not production recommendation |
| Device-specific key set during first commissioning | Avoids factory key inventory but has no trustworthy initial identity unless an existing secure channel exists | Not sufficient as the only MVP identity proof |
| Full hardware attestation/eFuse-backed identity | Strongest device identity when the complete key/eFuse/firmware chain is verified | `OPEN`; exact ESP-IDF/eFuse workflow and manufacturing ownership are not present in the repository |

### 11.2 Physical button and SoftAP decision

The button has one authority: it opens a local commissioning window and permits
the device to produce a fresh challenge signature. It does not prove Store
ownership, factory enrollment or user identity by itself.

Recommended initial hardware values for validation:

- Commissioning window: 60 seconds after a deliberate long press of 3 seconds.
- LED: slow double-blink while the window is open, rapid blink during local
  exchange, solid success indication for 5 seconds, and distinct error blink
  before returning to idle.

These values are `PROPOSED` test defaults, not final product decisions; button
debounce, accidental activation, visibility and user accessibility must be
validated on the actual enclosure/board.

SoftAP protection is layered:

1. WPA2 password protects association and must not be derived from MAC/SSID.
2. HTTPS protects the local exchange where the ESP32 certificate can be
   validated.
3. Certificate validation is required; certificate pinning is recommended only
   if the app can safely ship/rotate the device trust material.
4. The physical-window challenge signature and API bootstrap verifier provide
   the actual device-bound proof; WPA2 alone is not ownership evidence.

Local TLS/pinning is not declared universally mandatory until the certificate
provisioning UX and ESP-IDF memory/rotation behavior are tested. Plaintext local
HTTP carrying Wi-Fi credentials or bootstrap material is not an acceptable
production default.

### 11.3 Provisioning-session schema proposal

J.2 adds a separate `ProvisioningSession` model rather than overloading
`DeviceStatus`:

```text
id, deviceId, storeId, actorAccountId
bootstrapVerifier, challengeHash, idempotencyKey
status: ACTIVE | REDEEMED | EXPIRED | LOCKED | REVOKED
attemptCount, maxAttempts(default 5), expiresAt(default +30 minutes)
lockedAt, consumedAt, revokedAt, lastAttemptAt, createdAt, updatedAt
```

Recommended constraints/indexes:

- Unique idempotency key scoped to the actor/device creation operation.
- At most one active session per Device using a PostgreSQL partial unique index.
- Index `(deviceId, status, expiresAt)` and `(actorAccountId, createdAt)`.
- Restrictive foreign keys to Device, Store and Account.
- Unique bootstrap verifier; no plaintext bootstrap value.

The implemented schema includes the enrollment public key, key version,
enrollment status/timestamps, provisioning state, composite Device–Store
reference, unique bootstrap verifier, scoped idempotency key and a PostgreSQL
partial unique index allowing only one ACTIVE session per Device. Redemption,
attempt counting and audit atomicity remain J.3 runtime responsibilities.

### 11.4 Atomic brute-force and concurrency behavior

Redeem must execute in one PostgreSQL transaction with a row lock or equivalent
conditional update:

1. Lock the provisioning session and target Device in a stable order.
2. Reject if status is not `ACTIVE`, expired, consumed, revoked or locked.
3. Verify the bootstrap verifier and device challenge signature.
4. On failure, atomically increment `attemptCount`; at 5, set `status=LOCKED`
   and `lockedAt`. Return a generic error.
5. On success, atomically consume the session, update provisioning/credential
   state and insert AuditEvent.
6. Commit before returning the one-time operational token.

There is no automatic counter reset. Recommended recovery is a new session after
an explicit short cooldown; the old locked session remains unusable. Cooldown
duration and operator unlock authority are `OPEN` operational decisions.
Concurrent redemptions produce one success; losers receive a stable invalid or
conflict result and cannot issue a second token.

### 11.5 Operational token response-loss recovery

The server generates a new high-entropy token, stores only its SHA-256 verifier,
and returns plaintext only in the successful redemption response. It never
stores enough information to reconstruct that plaintext and never returns it
from a read endpoint.

If the server commits but the response is lost:

- The device must not assume retrying the same request will reveal the token.
- The idempotency key prevents a second issuance for the same redemption.
- The current Owner must physically reopen commissioning and request a new
  recovery session. That transaction revokes the unusable credential, rotates
  the verifier and writes `DEVICE_CREDENTIAL_ROTATED`.
- The old session/token is never returned; recovery is audited without secrets.

This favors no plaintext secret recovery over seamless automatic retry.

### 11.6 Ownership, provisioning and connectivity separation

J.2 must keep these concerns separate:

| Concern | Source of truth | Examples |
|---|---|---|
| Ownership | Device/Store relation plus StoreMembership authorization | Which Store owns the Device; who may reprovision |
| Provisioning lifecycle | ProvisioningSession and credential/enrollment state | Pending, active session, redeemed, locked, needs reconnection |
| Operational connectivity | Device status/last-seen telemetry | Online, offline, disabled, lastSeenAt |

`ONLINE`/`OFFLINE` must not encode ownership or bootstrap state. The current
`DeviceStatus` is insufficient for the complete state machine and must be
extended additively or paired with a separate provisioning state model.

### 11.7 J.1.1 decision classification

`APPROVED` from existing policy: bootstrap TTL 30 minutes, five failed attempts,
separate bootstrap/operational credentials, HTTPS bearer operational auth,
server-side Owner membership checks, physical reset not being transfer, and
same-transaction AuditEvent.

`APPROVED`: USB + controlled commissioning tool for initial device enrollment,
prototype scope without mandatory Secure Boot/flash encryption/eFuse writes,
and Owner app as the official provisioning flow after registration.

`PROPOSED`: 60-second/3-second button defaults, challenge-signature proof,
the exact enrollment-key representation, no automatic attempt reset, new-session
recovery after response loss, and the endpoint shape in this document. The
J.2 schema foundation for a separate ProvisioningSession is `IMPLEMENTED`.

`OPEN`: production manufacturing key injection, Secure Boot/flash-encryption/
eFuse configuration and verification, local TLS/pinning/QR UX, cooldown
duration, operator unlock authority and production enrollment-key rotation.

`DEFERRED`: ownership transfer, multiple active Owners, full hardware
attestation rollout, automated retention deletion and FCM delivery/outbox.

## 12. J.3 implementation contract

The J.3 prototype implementation provides these routes:

| Method | Path | Actor | Purpose |
|---|---|---|---|
| `POST` | `/v1/operator/devices/:deviceId/enrollment` | Injected commissioning operator authorizer | Register the enrollment public key |
| `POST` | `/v1/operator/devices/:deviceId/enrollment/revoke` | Injected commissioning operator authorizer | Revoke enrollment and active sessions |
| `POST` | `/v1/stores/:storeId/provisioning-sessions` | Authenticated, verified Owner | Create a new or recovery session |
| `GET` | `/v1/stores/:storeId/provisioning-sessions` | Authenticated, verified Owner | List safe session state |
| `GET` | `/v1/stores/:storeId/provisioning-sessions/:sessionId` | Authenticated, verified Owner | Read safe session state |
| `POST` | `/v1/stores/:storeId/provisioning-sessions/:sessionId/cancel` | Authenticated, verified Owner | Revoke an active session |
| `POST` | `/v1/devices/:deviceId/provisioning-sessions/:sessionId/redeem` | Device possession proof | Verify and issue the operational token once |

The enrollment authorizer is dependency-injected. The API does not trust
localhost, USB transport, Device ID or a client-supplied actor as authorization.
No commissioning credential is hardcoded in the repository.

### 12.1 Signature contract

J.3 uses `ECDSA_P256_SHA256_DER`:

- Enrollment public key: DER SubjectPublicKeyInfo, base64-encoded and stored as
  public metadata only.
- Signature: DER-encoded ECDSA signature, base64-encoded in the redeem request.
- Canonical UTF-8 bytes are exactly:

```text
pulselink-provisioning-v1\n<sessionId>\n<deviceKey>\n<challenge>\n<expiresAtEpochSeconds>
```

`challenge` is the base64url value returned when the session is created; the
database stores only its SHA-256 hash. `expiresAtEpochSeconds` is the
server-issued session expiry. Unsupported key types and malformed signatures
fail closed.

### 12.2 Redeem and recovery semantics

Redeem conditionally consumes the ACTIVE session inside a PostgreSQL
transaction. Only the request that changes the session to `REDEEMED` can update
`Device.deviceSecretHash` and commit its `AuditEvent`; concurrent valid requests
cannot both issue a credential. Invalid requests increment `attemptCount` with
a conditional update; the fifth effective failure sets `LOCKED` and the counter
is never automatically reset.

Plaintext bootstrap material, challenge and operational tokens are excluded
from logs and audit metadata. If a response is lost after commit, the old token
cannot be recovered; the Owner creates a recovery session and a later redeem
rotates the verifier. The old token is never returned.
