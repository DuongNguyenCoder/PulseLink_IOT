## Trusted enrollment implementation

### Contract

Only `POST /v1/operator/devices/:deviceId/enrollment` remains. It is registered
only when operator enrollment is enabled and an operator authorizer is
configured. The existing authorizer resolves the Device's persisted Store and
requires an active `DEVICES_WRITE` grant for that Store. The Owner self-service
enrollment route has been removed so an Owner API client cannot directly bind
an arbitrary public key as trusted identity. Owners may still manage/link their
Store's Device under the existing API contract; commissioning requires the
Device to have completed operator/factory enrollment.

The request body now contains:

```json
{
  "publicKeySpkiBase64": "canonical DER SubjectPublicKeyInfo, standard base64",
  "keyVersion": 1,
  "challenge": "32 random bytes encoded as unpadded base64url",
  "expiresAt": 1793200000,
  "signatureDerBase64": "DER ECDSA P-256 signature, standard base64"
}
```

The signature is ECDSA P-256/SHA-256 over UTF-8 fields joined by LF, with no
trailing LF:

```text
pulselink-device-enrollment-v1
<deviceKey>
<keyVersion decimal>
<canonical publicKeySpkiBase64>
<challenge>
<expiresAt unix seconds decimal>
```

The server requires a 32-byte canonical base64url challenge and expiry after
the current time but no more than five minutes ahead. It verifies the SPKI is
canonical standard base64 and is a P-256 key, bounds the DER signature, and
verifies the proof against that exact key. The Device key, version, SPKI,
challenge and expiry are all signed. The authorized operator must obtain this
proof from the actual device key through an approved factory channel; the
backend does not treat a SoftAP-provided key as trusted.

The service conditionally updates only a Device still `UNENROLLED`, enabled and
not revoked, inside a transaction. This makes replay on the same Device and
concurrent enrollment claims fail. The challenge is generated by the trusted
factory/operator workflow rather than persisted as a server challenge record;
the proof is short-lived and device-bound, and one-time consumption is enforced
by the Device state transition. A captured valid proof can at most race to
install the same signed key for that Device; it cannot substitute a different
key or enroll a different Device.

### Per-Device key uniqueness

`Device.enrollmentPublicKey` is now unique when non-null. PostgreSQL permits
multiple NULLs in the unique index, so un-enrolled Devices remain unaffected.
The new migration is:

`20261028204500_unique_device_enrollment_key/migration.sql`

Before applying it, a read-only check on the dedicated test database found zero
duplicate non-null enrollment key groups. Prisma status showed this single
migration pending; `migrate deploy` applied only this migration to the test DB.
No other database was migrated.

### What is still missing

No factory utility or firmware runtime currently returns an enrollment proof
from the protected on-device key. The existing identity provider source is
conditional on encrypted NVS, and NVS Encryption is disabled in the local
operational configuration. The backend contract is ready for a trusted
operator/factory client, but a new board cannot be considered enrolled until
the actual per-board public key and signed proof arrive over an approved path.

## Protected storage assessment

Source inspection reconfirmed:

- `CONFIG_PULSELINK_DEVICE_IDENTITY_NVS_PROVIDER` defaults off and depends on
  `CONFIG_NVS_ENCRYPTION`.
- `CONFIG_PULSELINK_OPERATIONAL_CREDENTIAL_STORAGE` defaults off and depends on
  `CONFIG_NVS_ENCRYPTION`; the operational credential storage module has only
  the interface/gate and no production NVS provider registration.
- `main.c` initializes ordinary NVS and does not initialize encrypted NVS keys
  through a reviewed key-provider or recovery path.
- The identity provider stores private DER in NVS in its conditional code path;
  no runtime evidence proves its key provisioning, protection or recovery.
- The local `sdkconfig` has NVS Encryption disabled. The isolated commissioning
  compile profile used for build validation does not enable the operational
  storage provider or provision keys.

No safe code change can truthfully make protected persistence production-ready
without deciding/provisioning the encryption-key custody and recovery mechanism.
Do not use plaintext NVS, a hardcoded encryption key, a build-time operational
token, or implicit identity regeneration as a fallback. No eFuse, NVS
Encryption, Flash Encryption or Secure Boot setting was changed; no board was
flashed, reset or erased.

### Required policy/operator decisions

1. Select key custody compatible with ESP32-S3 and ESP-IDF 5.5.5: hardware
   HMAC/eFuse-backed NVS key protection or an explicitly approved encrypted
   flash key-partition scheme. Specify exact provisioning ownership and access.
2. Define whether Flash Encryption/Secure Boot are prerequisites, who provisions
   them, production mode, recovery after interrupted provisioning, and how a
   failed/returned device is handled.
3. Define factory reset, key rotation, credential revocation, replacement
   board and Store transfer behavior.
4. Authorize the exact hardware provisioning/flash actions only after the
   procedure and recovery path have been reviewed.
5. Implement and test secure NVS initialization, storage adapter, read-back,
   reboot/power-loss behavior and failure recovery as one reviewed change.
