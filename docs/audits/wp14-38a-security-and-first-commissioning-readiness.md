## Executive summary

This increment adds a proposed storage/trust ADR, a cross-runtime enrollment
transcript fixture and a backend request builder that targets the existing
operator enrollment endpoint. The firmware can produce the canonical
enrollment payload bytes; the backend unit test verifies those exact bytes
against the same public test fixture. The request builder verifies a supplied
signature and formats a request, but does not sign, send, authenticate an
operator, or prove that the key belongs to the physical board.

The preflight can now probe a specifically approved public development host,
but only when the caller supplies an exact hostname allow-list value. It uses
HTTPS certificate/hostname validation, refuses redirects, and issues only GET
requests to `/health/live` and `/health/ready`. Both checks passed in a direct
retry. Preflight overall remains blocked by local firmware/profile/storage
readiness. No non-health API was contacted.

Overall remains **PARTIALLY COMPLETED**. No factory proof channel or approved
protected-storage provisioning/recovery policy is present. No hardware action
was performed.

## Architecture decision

The new [ADR](../architecture/adr/wp14-device-identity-and-credential-storage.md)
compares encrypted NVS with HMAC-backed per-device keys, encrypted NVS keys
protected by Flash Encryption, Flash Encryption alone, Secure Boot v2, a
possible secure element, and software/shared-key approaches. It recommends
HMAC-backed encrypted NVS as the storage candidate, with Secure Boot v2
considered independently for firmware authenticity. No exact eFuse key ID or
block is selected. The ADR is **proposed, not approved**.

The owner/operator stated responsibility for production provisioning and
recovery. The mechanism, authorized station/role, key custody, recovery steps,
factory reset, rotation/revocation and replacement-board policy remain to be
recorded and approved. The recommendation is not authorization to burn eFuses,
enable security modes, flash, erase or reset hardware.

## Trusted enrollment implementation

- Firmware `device_provisioning_build_enrollment_payload()` now encodes the
  existing domain-separated proof payload with the agreed newline-delimited
  fields. The implementation validates bounded single-line fields, a
  32-byte-base64url challenge, nonzero key version/expiry and output capacity.
- `firmware/esp32/tests/fixtures/device_enrollment_v1.hex` is a public-only
  shared vector. C host execution compares generated bytes against it.
- The backend `buildDeviceEnrollmentRequest()` validates input with Zod,
  checks the current expiry and ECDSA proof using the supplied SPKI, and
  constructs `POST /v1/operator/devices/:deviceId/enrollment` with the
  existing proof body. The Device key is signed into the proof by the existing
  contract; server-side Device/Store binding and operator authorization remain
  authoritative.
- The CLI reads bounded JSON from stdin and prints a request structure only.
  It does not make an HTTP request or accept an operator bearer token.

This is codec/request preparation only. A locally generated key in a unit test
does not establish board identity. Gate B is **BLOCKED** until an approved
board-origin challenge/signature channel exists and is verified on the actual
board. No enrollment request was submitted.

## Operator decisions and actions

1. **Approve storage/security policy:** choose the proposed per-device
   HMAC-backed encrypted NVS route or the Flash-Encryption-protected NVS-key
   alternative. Record key custody, unique per-board provisioning,
   power-loss/recovery, factory-reset, revocation, rotation, lost/replacement
   board handling, and the production operator/station. Separately decide
   whether Secure Boot v2 and Flash Encryption are production requirements.
   No exact eFuse key ID/block should be selected outside that reviewed plan.
2. **Approve the board proof interface:** provide the exact ESP32-S3 board
   revision and schematic and authorize a specific factory proof transport
   that yields only SPKI and a short-lived signature from the board-held key.
   The owner/operator responsibility is acknowledged; the physical channel
   and its DTR/RTS/reset behavior are not established.
3. **After decisions 1–2:** authorize the precise hardware operations needed
   (if any) separately, then implement and verify the factory adapter and
   protected NVS path. Do not open the serial port before reset behavior and
   the test action are approved.
4. **For first physical commissioning:** provide an isolated test router and
   approve use of its test credentials at the time of the hardware run. No
   credentials have been transferred in this increment. Confirm the API
   origin and CA/trust path from the actual phone and board, not just this
   workstation.
5. Run the existing operator/Owner flow only after the enrollment and storage
   gates are closed; capture redacted enrollment/replay, redemption,
   persistence/read-back/reboot, authenticated status, event commit/ACK and
   duplicate-retry evidence.
